# AGENTS.md

Инструкции для AI-агентов, работающих с репозиторием **NewMishka/inbox-weaver**.

Область действия: весь репозиторий, если в подкаталоге нет более специфичного `AGENTS.md`.

## 1. Что это за проект

**InboxWeaver — Менеджер писем 2.0** — WebExtension для Thunderbird-подобного почтового клиента. Расширение проверяет письма по пользовательским правилам, ведёт аудит и статистику, позволяет **вручную** сохранять подходящие вложения и формирует XLSX-отчёты.

Текущая релизная линия:

- `manifest.json`: версия `2.0`;
- функциональная база 2.0: `1.0.230 / test62`;
- production reference для сравнения и отката: `1.0.162`;
- переход `1.0.230 → 2.0` изначально является релизной упаковкой и документацией, а не новой реализацией обработки писем;
- пока ручной протокол `P-001–P-057` не подтверждён, **не называй 2.0 production baseline**.

Перед существенными изменениями прочитай:

1. `README.md`;
2. `CONTEXT.md`;
3. `docs/ARCHITECTURE_RULES.md`;
4. `docs/ARCHITECTURE.md`;
5. `docs/DEVELOPMENT_GUIDE.md`;
6. для релизных изменений — `docs/BASELINE.md`, `docs/TEST_PLAN.md`, `docs/RELEASE_PROCESS.md`.

Архитектурные решения зафиксированы в `docs/DECISIONS.md`, известный долг — в `docs/TECHNICAL_DEBT.md`.

## 2. Неприкосновенные продуктовые инварианты

Не меняй эти правила без явной задачи и отдельного объяснения последствий.

### Проверка не равна сохранению

Проверка письма по правилам **не должна автоматически сохранять вложения**.

Физическое сохранение разрешено только по явному пользовательскому действию и через общий pipeline с `saveAttachments: true`.

Это касается:

- Live-обработки новых писем;
- startup catch-up;
- полного/принудительного обхода;
- retry;
- тестирования правил.

### Один pipeline письма

Manual, Live, startup catch-up, force scan и retry должны использовать `core/messageProcessingService.mjs`.

Не создавай параллельную реализацию обработки письма в UI, `background.js` или отдельном сервисе.

### Ошибка одного письма локальна

Ошибка Thunderbird API для конкретного письма:

- фиксируется в аудите/диагностике;
- возвращается как формализованный `status: 'error'`;
- содержит `mailOperation`, если ошибка связана с почтовым API;
- **не должна останавливать полный обход остальных писем**.

Текущий лимит ожидания почтовой операции — 45 секунд через `modules/operationTimeout.mjs`.

### Дедупликация только по содержимому

Основной идентификатор одинакового вложения — SHA-256 фактических байтов файла.

- не используй имя файла, тему, отправителя или путь как ключ уникальности;
- fingerprint допустим только для совместимости старых записей;
- сохраняй семантику reserve → commit/release;
- не освобождай запись реестра без подтверждённого основания.

### Статистика — проекция

`attachmentLogs`, `messageAuditLogs` и `exportRegistry` — источники бизнес-состояния.

Статистика и XLSX являются вычисляемой проекцией. UI не должен превращать агрегированные значения в новый источник истины.

### Устойчивый идентификатор письма

Для отчётов и долговременной идентификации используй RFC `Message-ID` (`headerMessageId`).

Внутренний Thunderbird `messageId` временный: он нужен для обращения к письму в текущем профиле/сессии, но не должен экспортироваться как устойчивый идентификатор.

## 3. Архитектурные границы

### `background.js`

Это **composition root**:

- создание сервисов;
- dependency injection;
- регистрация Thunderbird events;
- связывание runtime-команд.

Не добавляй сюда новую бизнес-логику проверки, дедупликации, статистики, обхода или сохранения.

### `core/*.mjs`

Сервисы пользовательских сценариев и orchestration:

- `messageProcessingService.mjs` — жизненный цикл одного письма;
- `forceExportService.mjs` — полный обход, прогресс, остановка;
- `startupCatchupService.mjs` — догоняющая проверка после запуска;
- `retryService.mjs` — повтор ошибок;
- `ruleTestService.mjs` — тестирование правил;
- `runtimeRouter.mjs` — единая маршрутизация UI-команд.

Новые внешние зависимости передавай через factory arguments, чтобы сервисы оставались тестируемыми.

### `modules/*.mjs`

Чистая или переиспользуемая логика: parsing/matching правил, storage, дедупликация, пагинация, статистика, XLSX, диагностика и вспомогательные операции.

Новые атомарные изменения storage выполняй через `storageManager.update`. Не добавляй новые прямые конкурирующие read-modify-write операции поверх `messenger.storage.local`.

### UI-каталоги

- `mainPopup/`;
- `rulesTab/`;
- `settingsTab/`;
- `statisticsTab/`;
- `auditTab/`.

UI инициирует команды и отображает состояние. Не дублируй в UI бизнес-правила сервисного слоя.

### Runtime messaging

Должен существовать один `runtimeRouter`. Не добавляй конкурирующие `runtime.onMessage` listeners для бизнес-команд.

## 4. Состояния и контракты

Допустимые состояния вложения:

```text
pending | success | duplicate | error | no_attachment
```

Пользовательский результат письма нормализуется через общий контракт `processingResult`.

Если меняешь контракт результата:

- найди всех производителей и потребителей;
- обнови тесты;
- проверь статистику, аудит, UI и XLSX;
- не вводи новое состояние только в одном слое.

## 5. Правила разработки

### Делай минимальное изменение

Не смешивай:

- исправление бага и крупный рефакторинг;
- изменение поведения и массовое форматирование;
- релизную документацию и несвязанные функциональные изменения.

Сохраняй текущие границы модулей, если задача прямо не требует архитектурной перестройки.

### Для регрессии сначала тест

Если ошибка воспроизводима на уровне чистой функции или сервиса:

1. добавь тест, который падает на текущем поведении;
2. внеси минимальное исправление;
3. запусти целевой тест;
4. запусти полный набор тестов.

Используется встроенный `node:test`; отдельного npm test script в репозитории нет.

### Не маскируй ограничения среды

Известная ошибка Thunderbird `messages.listAttachments` для отдельных MIME/IMAP-сообщений может возвращать `An unexpected error occurred`.

Не превращай её в «успех». Правильное поведение — локальная ошибка письма + аудит + продолжение обхода.

### Диагностика должна оставаться безопасной

Новые диагностические данные перед экспортом должны проходить обезличивание.

Не выводи без необходимости:

- абсолютные пользовательские пути;
- email;
- имена аккаунтов;
- имена вложений;
- содержимое правил;
- иные чувствительные данные профиля.

Ошибка диагностического модуля не должна ломать основную обработку письма.

## 6. Обязательные проверки

Минимум перед завершением любой кодовой задачи:

```bash
node --test test/*.test.mjs
node --check background.js
find core modules mainPopup rulesTab settingsTab statisticsTab auditTab -type f \( -name '*.js' -o -name '*.mjs' \) -print0 | xargs -0 -n1 node --check
git diff --check
```

Если менялся только ограниченный набор JS/MJS-файлов, во время разработки можно запускать `node --check` адресно, но перед релизным выводом используй полный набор выше.

Не заявляй, что тесты прошли, если ты их фактически не запускал.

Автоматические тесты **не заменяют** ручную проверку Thunderbird, почтовой синхронизации, Downloads API и файловой системы.

## 7. Ручная проверка

Для изменений, затрагивающих интеграцию с клиентом, явно отмечай, что требуется ручной smoke.

Особенно важны:

- обновление расширения без потери правил и настроек;
- LiveMail;
- startup catch-up;
- полный обход и его остановка;
- ручное сохранение вложений;
- одинаковые байты под разными именами;
- удаление/повторное сохранение файлов;
- статистика, фильтры и группировки;
- XLSX;
- диагностический снимок;
- сброс;
- сценарии `P-001–P-057`.

Не проставляй PASS за пользователя и не объявляй production-готовность по одним unit-тестам.

## 8. Сборка XPI

XPI должен быть воспроизводимым и собираться **из зафиксированного commit**, а не из незакоммиченного рабочего дерева.

Полная проверка:

```bash
node --test test/*.test.mjs
node --check background.js
find core modules mainPopup rulesTab settingsTab statisticsTab auditTab -type f \( -name '*.js' -o -name '*.mjs' \) -print0 | xargs -0 -n1 node --check
git diff --check
git status --short
bash scripts/build-xpi.sh HEAD /tmp/inbox-weaver-v2.0.xpi
unzip -t /tmp/inbox-weaver-v2.0.xpi
sha256sum /tmp/inbox-weaver-v2.0.xpi
```

Для релиза предпочтительно передать конкретный commit SHA вместо `HEAD`.

Не перезаписывай опубликованный XPI с тем же именем другим содержимым. Для артефакта фиксируй:

- версию;
- commit SHA;
- SHA-256;
- результаты автоматических проверок;
- фактический статус ручной приёмки.

## 10. Git и PR

Следуй `CONTRIBUTING.md`:

- одна задача — одна ветка;
- baseline напрямую не меняется;
- крупный рефакторинг не смешивается с исправлением бага;
- рабочая ветка → `develop` → релизная ветка → `main`;
- прямые изменения `main` — только для экстренной документации/администрирования.

Типичные имена:

```text
fix/<problem>
feature/<feature>
docs/<topic>
refactor/<area>
```

Типичные commit prefixes:

```text
fix:
feat:
docs:
test:
refactor:
```

Перед merge в PR укажи:

- что и зачем изменено;
- затронутые файлы;
- риски и ограничения;
- какие автоматические проверки выполнены;
- что требует ручной проверки;
- Issue, если есть;
- тестовый XPI и его SHA-256, если собирался.

## 11. Известный технический долг — не исправлять «заодно»

Сейчас осознанно остаются:

- полная сериализация больших массивов storage;
- последовательный полный обход;
- отсутствие восстановления SHA-реестра после полного удаления/переустановки расширения;
- заглушка `storageManager.migrate()` без реальной схемы миграций;
- ограничения `messages.listAttachments`;
- частичный backfill старых записей без `headerMessageId`.

Не превращай локальную задачу в скрытую переработку этих областей. Если долг мешает корректному исправлению, остановись и явно опиши необходимость отдельной задачи.

## 12. Что агент должен сообщить в финале

После изменений дай краткий отчёт:

2. почему;
3. какие файлы затронуты;
4. какие тесты/проверки фактически выполнены и их результат;
5. что не удалось проверить автоматически;
6. риски, ограничения и нужный ручной smoke;
7. нужен ли changelog/release note/XPI.


## 13. Оркестрация с ChatGPT Plugins / MCP

Если среда предоставляет подключённые плагины/коннекторы, используй их автоматически по назначению. Пользователь не обязан каждый раз писать `@GitHub`, `@GitBook`, `@Context7` и т. п.

Не запускай все инструменты механически для каждой задачи: выбирай только те, которые реально уменьшают риск ошибки или нужны для выполнения работы.

### GitHub — исходный код и инженерная история

**GitHub является основным источником истины для кода, тестов и версионируемой документации.**

Используй GitHub для:

- чтения актуальной ветки, commits, PR и Issues;
- анализа diff и истории изменений;
- создания рабочих веток/commit/PR;
- проверки CI, если он настроен;
- подготовки release notes и GitHub Release;
- сверки версии, тега, commit SHA и артефактов.

Перед изменением всегда убеждайся, что работаешь с правильной веткой. Для текущей линии 2.0 это может быть `release/2.0-from-1.0.230`, но не считай её вечным default: проверяй задачу и состояние репозитория.

Не merge PR, не создавай/публикуй GitHub Release и не меняй baseline без явного разрешения пользователя.

### Superpowers — процесс разработки

Для нетривиальной функциональности, регрессии, архитектурной задачи или сложной отладки используй доступные Superpowers-практики:

```text
понимание задачи
→ анализ текущего поведения
→ план
→ тест, воспроизводящий проблему
→ минимальное изменение
→ целевые тесты
→ полный regression run
→ проверка diff
→ отчёт
```

Для простой правки текста, опечатки или очевидного локального изменения не раздувай процесс искусственно.

### Context7 — актуальные внешние API и библиотеки

Используй Context7, когда решение зависит от поведения внешнего API/библиотеки, которое не доказано самим репозиторием.

Особенно это относится к:

- Thunderbird/WebExtension API;
- `messenger.messages.*`;
- `messenger.downloads.*`;
- `messenger.storage.*`;
- `messenger.alarms`;
- особенностям Manifest/WebExtension;
- сторонним библиотекам, если они появятся в проекте.

Правило приоритета:

```text
код и тесты репозитория
→ зафиксированные ADR/документация проекта
→ актуальная официальная документация / Context7
→ предположение
```

Предположение не выдавай за факт. Если Context7 не содержит нужной документации, используй официальный upstream-источник и явно укажи ограничение.

### GitBook — публичная документация проекта

GitBook используется как **публичный слой документации**, а не как независимый источник бизнес-логики.

Источник истины для изменяемой технической документации остаётся в GitHub. Поток обновления:

```text
изменение кода/поведения
→ тесты
→ README / docs / CHANGELOG в GitHub
→ GitBook Change Request
→ preview/review
→ merge/publish после подтверждения пользователя
```

При изменении пользовательского поведения проверь необходимость обновить в GitBook:

- обзор продукта;
- установку и обновление;
- работу с правилами;
- проверку писем и Live/catch-up;
- сохранение вложений и дедупликацию;
- статистику и XLSX;
- диагностику и решение проблем;
- release notes;
- архитектуру и раздел для разработчиков.

Не копируй внутренние документы в публичный GitBook механически. `TECHNICAL_DEBT.md`, внутренние детали приёмки, диагностические ограничения и служебные документы публикуй только в форме, подходящей внешнему пользователю.

Для `inbox-weaver` должен использоваться **отдельный GitBook site/space**, а не документация другого проекта.

Если GitBook site ещё не создан:

1. подготовь структуру и контент на основе GitHub;
2. покажи план пользователю;
3. после подтверждения создай отдельный site/space;
4. вноси содержательные изменения через GitBook Change Request;
5. сначала проверяй preview;
6. merge/publish выполняй только после явного разрешения.

Не исправляй расхождение GitHub ↔ GitBook молча: укажи, какая сторона устарела, и синхронизируй от GitHub как от канонического источника.

### Whimsical — схемы и визуализация

Используй Whimsical, если диаграмма действительно упрощает понимание:

- message-processing pipeline;
- Live / catch-up / force scan;
- дедупликация reserve → commit/release;
- storage/statistics projection;
- release workflow.

Диаграмма является дополнением. Ключевой архитектурный контракт всё равно должен быть описан текстом в репозитории.

Не меняй архитектуру только ради более красивой схемы.

### Google Drive — вспомогательные артефакты

Google Drive используй только там, где пользователь явно хочет хранить/передавать тестовые материалы или внешние артефакты.

Не делай Drive источником истины для кода, документации или версии XPI.

Не загружай туда:

- секреты;
- пользовательские почтовые данные;
- необезличенные диагностические выгрузки;
- новый релизный XPI

без явного указания пользователя.

Для опубликованного релиза предпочтительны GitHub Release + commit SHA + SHA-256.

## 14. Стандартные агентские сценарии

### «Проверь проект»

Выполни:

```text
GitHub: состояние ветки, diff, PR/Issues
→ архитектурные инварианты
→ релевантные тесты
→ полный автоматический прогон
→ Context7/официальные API-доки при спорных внешних контрактах
→ отчёт без публикации изменений
```

### «Исправь проблему»

Выполни:

```text
GitHub
→ Superpowers / systematic debugging
→ воспроизводящий тест
→ минимальный fix
→ target tests
→ полный regression run
→ docs/changelog при необходимости
→ PR или commit в согласованную ветку
```

### «Подготовь релиз»

Выполни:

```text
GitHub: версия + история + release diff
→ Superpowers: release checklist
→ Context7: только для затронутых внешних API
→ полный test/syntax/diff-check
→ воспроизводимая сборка XPI
→ unzip -t + SHA-256
→ README/CHANGELOG/release notes
→ GitBook draft/Change Request
→ итоговый отчёт
```

После этого остановись перед необратимыми действиями и запроси/используй явное разрешение на:

- merge в релизную ветку или `main`;
- публикацию GitHub Release;
- публикацию/merge GitBook Change Request;
- загрузку внешних артефактов.

### «Опубликуй релиз»

Если пользователь уже явно дал разрешение на публикацию, после всех обязательных проверок разрешено выполнить согласованные write-actions в GitHub и GitBook. Не расширяй разрешение на несвязанные действия.
