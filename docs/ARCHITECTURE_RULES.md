# Архитектурные правила

Статус: действуют для линии `1.0.227+`.

## 1. Background — только composition root

В `background.js` разрешены создание сервисов, внедрение зависимостей и регистрация Thunderbird events/runtime-команд. Бизнес-логика выносится в `core` или `modules`.

## 2. Один pipeline письма

Manual, live, startup catch-up, force scan и retry вызывают `messageProcessingService`. Параллельные альтернативные реализации запрещены.

## 3. Явные зависимости

Доступ к Thunderbird API, журналированию и сохранению передаётся сервисам через factory arguments, если это необходимо для тестирования.

## 4. Storage через общий слой

Новые атомарные изменения выполняются через `storageManager.update`. Прямой доступ legacy UI допускается временно и зарегистрирован как технический долг.

## 5. Формализованные состояния

Допустимые состояния вложения:

```text
pending | success | duplicate | error | no_attachment
```

Пользовательский результат письма формируется единым контрактом `processingResult`.

## 6. Дедупликация по байтам

SHA-256 фактического буфера — единственный надёжный идентификатор содержимого. Fingerprint используется только для совместимости старых записей.

## 7. Статистика — проекция

UI и XLSX используют `statisticsAggregator`. Они не должны самостоятельно пересчитывать или изменять бизнес-состояния.

## 8. Безопасная очистка

Удаляются только объекты, зарегистрированные плагином. Перед очисткой собираются точные ссылки, после операции сохраняется диагностика.

## 9. Один runtime router

Все UI-команды регистрируются в одном `runtimeRouter`; несколько конкурирующих `onMessage` listeners запрещены.

## 10. Тест перед исправлением

Для воспроизводимой регрессии добавляется тест сервиса или чистой функции. Обязательны полный прогон, syntax check и `git diff --check`.

## 11. Артефакт воспроизводим

XPI собирается только из commit и сопровождается SHA-256. Файл с тем же именем не заменяется другим содержимым.

## 12. Ручная приёмка обязательна

Автоматические тесты не подтверждают интеграцию с реальным профилем Thunderbird, почтовой синхронизацией и файловой системой.

## 13. Ошибка одного письма локальна

Ошибка почтового API конкретного письма должна быть записана в аудит вместе с
названием операции и возвращена как формализованный ошибочный результат. Она
не должна аварийно завершать полный обход остальных писем.
