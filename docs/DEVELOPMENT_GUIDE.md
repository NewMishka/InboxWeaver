# Руководство разработчика

## Точки входа

- `background.js` — composition root и регистрация Thunderbird events;
- `core/messageProcessingService.mjs` — обработка одного письма;
- `core/startupCatchupService.mjs` — восстановление после запуска;
- `core/forceExportService.mjs` — принудительный обход;
- `core/runtimeRouter.mjs` — команды UI;
- `modules/statisticsAggregator.mjs` — проекция статистики;
- `modules/duplicateManager.mjs` — SHA-реестр.
- `modules/developerLog.mjs` — ограниченный журнал и обезличенный диагностический снимок.
- `modules/operationTimeout.mjs` — общий лимит ожидания почтовых операций (45 секунд).

## Архитектурные правила

- UI не записывает бизнес-состояния вложений напрямую.
- Любой путь обработки вызывает единый `messageProcessingService`.
- Физическое сохранение выполняется только при `saveAttachments: true`.
- Статистика не должна становиться источником истины.
- Новая внешняя зависимость передаётся в сервис через factory arguments.
- Runtime-команда регистрируется только в едином router.
- Часто обновляемое состояние UI хранится одним последним снимком, а не потоком событий.
- Новые диагностические поля проходят обезличивание перед экспортом.
- Ошибка внешнего почтового API должна содержать `mailOperation`; для ожидаемой ошибки одного письма возвращается формализованный результат `status: 'error'`, а не падает весь обход.

## Проверки перед commit

```bash
node --test test/*.test.mjs
node --check <изменённые js/mjs>
git diff --check
```

Для исправления регрессии сначала добавляется воспроизводящий тест чистой функции или сервиса, затем изменение кода.
