# Технический долг

Актуально для функциональной базы `1.0.230` и предварительной версии 2.0.

## Высокий приоритет

- Монолитные массивы журналов и реестра всё ещё требуют полной сериализации
  при добавлении записи; батчинг в 1.0.211 снижает частоту записи при полном
  обходе (раз в 25 писем/1с вместо каждого письма), но не убирает полную
  перезапись массива как таковую — нужны страничное хранение и постоянные
  индексы. `modules/storageManager.mjs:appendToArray/appendManyToArray`
  по-прежнему делают полный `get → push/concat → set`.
- Полный обход остаётся последовательным (`core/forceExportService.mjs`:
  вложенные `for...of` по аккаунтам/папкам/письмам); нужна ограниченная
  очередь после измерения безопасного уровня параллелизма в целевом
  почтовом клиенте.
- Реестр дублей не восстанавливается после полного удаления/переустановки
  расширения: `storage.local` теряет данные, а файлы на диске остаются, и
  первый повторный обход может создать настоящий дубль. Сверка при старте
  (1.0.211, `reconcileExportRegistry`) закрывает только случай «реестр
  помнит файл, которого больше нет», а не обратный.
- `modules/storageManager.mjs:migrate()` — заявленная версионированная
  миграция схемы `storage.local` является заглушкой (всегда возвращает
  `{status:'ok', reason:'No schema migration required'}`) и нигде не
  вызывается в коде. Либо реализовать реальные миграции, либо удалить как
  мёртвый код.
- Thunderbird может возвращать нерасшифрованную ошибку `An unexpected error occurred` для `messages.listAttachments` отдельных писем с нестандартной MIME-структурой или недоступными IMAP-частями. Версия `1.0.227` безопасно фиксирует и пропускает такое письмо, но первопричина недоступна из WebExtension API; требуется ручная проверка исходных писем/сервера.

1. Реализовать версию схемы `storage.local` и явные миграции (или удалить неиспользуемую заглушку `migrate()`).
2. Снизить стоимость чтения/перезаписи журналов до 20 000 строк и добавить версионированную ротацию.
3. Выполнить ручную приёмку startup catch-up и удаления файлов в целевой среде.
4. Завершить ручной протокол 2.0 и решить вопрос о production-статусе.

## Средний приоритет

1. Разделить `messageProcessingService.mjs` на metadata и attachment workflow при следующем изменении поведения.
2. Добавить browser-level тесты UI таблиц и `rowspan`-группировки.
3. Централизовать коды ошибок и пользовательские сообщения.
4. Добавить browser-level проверку диагностического снимка и загрузок JSON.

## Принятые ограничения

- WebExtension не имеет произвольного нативного доступа к файловой системе.
- Достоверность `fileExists` зависит от Thunderbird Downloads API.
- Локальные автоматические тесты не заменяют проверку реального профиля и почтовой синхронизации.
- Сверка реестра дублей при старте (ADR-014) может ошибочно освободить запись,
  если Thunderbird уже очистил историю загрузок для существующего файла —
  осознанный компромисс в пользу снятия постоянной блокировки пересохранения.
- Старые журналы без `headerMessageId` восстанавливают RFC `Message-ID` при
  экспорте через доступный в текущей сессии внутренний ID Thunderbird. Это
  бэкфил без записи в storage и потому остаётся частичным: если исходное
  письмо недоступно, `message_id` остаётся пустым; внутренний ID в отчёт не
  подставляется.
