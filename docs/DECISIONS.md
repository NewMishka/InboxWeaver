# Архитектурные и продуктовые решения

Решения линии 1.0.162–1.0.230, сохранённые в версии 2.0.

## ADR-001 — Baseline

**Статус:** принято.

`1.0.162` является production reference. Версия 2.0 подготовлена из кандидата `1.0.230`; её ручная приёмка ещё ожидается.

## ADR-002 — Ручное сохранение

**Статус:** принято.

Автоматическая обработка проверяет письмо по правилам и создаёт состояние `pending`. Физическое сохранение запускается только кнопкой пользователя.

## ADR-003 — Дедупликация

**Статус:** принято.

- идентичность файла определяется SHA-256 фактических байтов;
- имя, тема и отправитель не являются ключом уникальности;
- один буфер используется для хеширования и записи;
- резервирование защищает параллельные операции;
- предупреждение ссылается на канонический реально сохранённый источник.

## ADR-004 — Источники истины

**Статус:** принято.

- `attachmentLogs` — журнал переходов состояния вложения;
- `exportRegistry` — SHA-реестр подтверждённых сохранений и резерваций;
- `messageAuditLogs` — аудит результата письма;
- статистика — вычисляемая проекция журналов, а не самостоятельное хранилище.

## ADR-005 — Фактически сохранённый файл

**Статус:** принято.

В KPI и таблицу сохранённых попадает только `success` с `fileExists !== false`. Наличие проверяется адресно через Thunderbird Downloads API по `downloadId`.

## ADR-006 — Обработка после запуска

**Статус:** принято.

Плагин хранит checkpoint активности и после запуска проверяет письма, пришедшие во время остановки. Проверка не сохраняет файлы автоматически.

## ADR-007 — Фоновая архитектура

**Статус:** принято.

`background.js` — composition root. Бизнес-логика размещается в сервисах:

- `messageProcessingService`;
- `startupCatchupService`;
- `forceExportService`;
- `ruleTestService`;
- `retryService`;
- `runtimeRouter`.

## ADR-008 — Источники артефактов

**Статус:** принято, обновлено для 2.0.

GitHub является каноническим источником кода, документации, PR и релизных артефактов. XPI публикуется как asset GitHub Release и сопровождается commit SHA и SHA-256. Внешние хранилища могут использоваться только как временный вспомогательный канал и не являются источником истины для релиза.

## ADR-009 — Безопасный сброс

**Статус:** принято, уточнено ADR-013.

`exportRegistry` очищается только после подтверждённого удаления зарегистрированных файлов. Если Downloads API возвращает `exists=true` или ошибку, соответствующая запись реестра сохраняется для защиты от повторной выгрузки — с 1.0.211 это решение применяется по каждому файлу отдельно, а не ко всему реестру сразу (см. ADR-013).

## ADR-010 — Диагностический снимок

**Статус:** принято.

Событийный журнал ограничен последними 1000 записями. Снимок объединяет окружение, счётчики, состояние тегов и UI; пользовательские пути, адреса, аккаунты, вложения и правила обезличиваются.

## ADR-011 — Несколько правил

**Статус:** принято.

Письмо остаётся одной бизнес-сущностью и одной строкой статистики, но хранит полный `matchedRules` и находится фильтром по любому совпавшему правилу.

## ADR-012 — Контекст производительной обработки

**Статус:** принято.

Правила, их синтаксические деревья, настройки и список аккаунтов образуют
неизменяемый runtime-контекст. Контекст переиспользуется между письмами и
инвалидируется при изменении `rules` или `settings`. Полное MIME-дерево письма
загружается только тогда, когда хотя бы одно применимое правило зависит от
`body:`.

Текущие задачи производительности: [Roadmap](../ROADMAP.md) и [технический долг](TECHNICAL_DEBT.md). Исторический план 1.0.210 доступен в истории Git.

## ADR-013 — Точечное освобождение реестра дублей

**Статус:** принято.

Освобождение записи `exportRegistry` по SHA-256 выполняется индивидуально для
каждого физически удалённого файла (`forgetExportByHash` вызывается из
`deleteDownloadedFiles` сразу после подтверждённого удаления), а не для всего
реестра целиком по признаку «все запрошенные файлы удалены без ошибок». Это
заменяет предыдущее правило ADR-009: неудачное удаление одного файла больше не
блокирует освобождение записей для остальных, успешно удалённых файлов.

## ADR-014 — Сверка реестра дублей при старте

**Статус:** принято.

При каждом запуске фонового процесса `reconcileExportRegistry` сверяет
закоммиченные записи `exportRegistry` с историей загрузок Thunderbird
(`messenger.downloads.search`) и освобождает записи, чей `downloadId`
подтверждённо отсутствует (`exists === false`) или не найден в истории вовсе.
Резервации в процессе сохранения и записи без `downloadId` не проверяются;
ошибка поиска оставляет запись как есть. Решение не устраняет обратный случай
— файлы, пережившие переустановку расширения при обнулении `storage.local`,
— поскольку Thunderbird не предоставляет способа обнаружить существование
файла, не зарегистрированного в его истории загрузок.

## ADR-015 — Локальная ошибка письма не останавливает полный обход

**Статус:** принято.

Полный обход продолжает работу после ошибки почтового API одного письма. Если
`messages.listAttachments` не возвращает список вложений, обработчик сохраняет
аудит «Ошибка», назначает метку ошибки и возвращает формализованный результат
`status: error`; `forceExportService` увеличивает `failedMessages` и переходит
к следующему письму. В журнале фиксируется `mailOperation`.

Это решение отделяет отказ отдельного MIME-сообщения или IMAP-части от отказа
ящика и не позволяет одному письму блокировать статистику всего обхода.
