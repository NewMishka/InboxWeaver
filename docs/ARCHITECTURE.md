# Architecture

Статус документа: архитектура функционального кода 1.0.230, использованного в 2.0.

## Логическая схема

```text
UI / Popup
    ↓
Settings and Rule Management
    ↓
Mail Processing / LiveMail
    ↓
Rule Matching
    ↓
Attachment Processing
    ↓
Storage
    ↓
Statistics
    ↓
Audit / Diagnostics
    ↓
Export
```

## Основные подсистемы

### Background composition root

`background.js` создаёт сервисы и связывает их с Thunderbird WebExtension API. В нём не должна появляться новая логика стартового обхода, принудительного сканирования или маршрутизации runtime-команд.

### Message Processing

`core/messageProcessingService.mjs` владеет полным жизненным циклом одного письма: загрузкой метаданных и вложений, выбором применимых правил, формированием `pending`, ручным сохранением, SHA-256 дедупликацией, аудитом и единым результатом обработки. Почтовые вызовы ограничены ожиданием 45 секунд. Если Thunderbird не отдаёт список вложений конкретного письма, сервис сохраняет аудит со статусом «Ошибка», назначает метку ошибки и возвращает формализованный ошибочный результат вместо выброса исключения.

Сервис получает внешние операции через зависимости и не регистрирует события Thunderbird самостоятельно.

### Rule Test

`core/ruleTestService.mjs` тестирует правила на ограниченной выборке писем, используя тот же parser, matcher и область аккаунта/папки, что и production-обработка.

### Retry

`core/retryService.mjs` выбирает последние ошибочные состояния и повторно запускает единый message-processing pipeline.

### Startup Catch-up

`core/startupCatchupService.mjs` отвечает за контрольную точку активности, поиск писем, пришедших во время остановки Thunderbird, и запуск проверки без автоматического сохранения.

### Force Export

`core/forceExportService.mjs` отвечает за обход выбранных аккаунтов и папок, публикацию прогресса и single-flight защиту принудительной проверки. Вызовы почтового API и обработка одного письма имеют ограничение ожидания в 45 секунд: недоступный ящик или письмо фиксируется как ошибка, после чего обход продолжается. Формализованный ошибочный результат письма также увеличивает `failedMessages`, сохраняет `lastFailedMessageId` и `lastFailedStage`, но не завершает обход аварийно. Во время обхода пользователь может запросить остановку: текущее письмо завершается, а следующие письма, страницы и папки не запускаются; накопленный прогресс сохраняется.

### Runtime Router

`core/runtimeRouter.mjs` предоставляет единственную точку маршрутизации сообщений UI к обработчикам фонового процесса.

### UI
Отвечает за взаимодействие с пользователем, создание правил, запуск операций, отображение статистики и диагностик.

### Rule Engine
Хранит и применяет условия правил к письмам и вложениям. Запросы компилируются
один раз в runtime-контекст, который также содержит зависимости правил от тела
письма и вложений.

### Rule Files

`modules/ruleFile.mjs` преобразует правила из локального представления в читаемый и редактируемый JSON-файл формата `inbox-weaver-rules` версии 1 и обратно. Импорт не записывает правила до успешной проверки формата и правил; пользователь выбирает замену текущего набора или добавление.

### Mail Processing
Получает данные писем, запускает обработку вручную или в Live-режиме. Данные
загружаются ступенчато: заголовок, затем необходимые вложения, затем полное
MIME-дерево только для правил по телу.

### Attachment Processing
Проверяет наличие и параметры вложений, формирует результат обработки.

### Storage
Сохраняет файлы и служебные данные, участвует в защите от повторной обработки.

### Duplicate Engine
Определяет, обрабатывался ли объект ранее, и предотвращает нежелательные дубли. Освобождение записи реестра по SHA-256 выполняется точечно при подтверждённом удалении файла и дополнительно сверяется с историей загрузок Thunderbird при старте фонового процесса.

### Statistics
Собирает показатели по обработанным письмам, вложениям, сохранениям и пропускам.
Фильтр по правилу использует только актуальные правила из хранилища, а не исторические имена из журналов.
`statisticsTab/statistics.js` умеет сохранять вложения не только по одному
письму, но и массово — кнопка «Сохранить все вложения» последовательно
вызывает тот же контракт `saveMessageAttachments`, что и одиночная кнопка,
по всем письмам, ожидающим сохранения, в области текущих фильтров и
сортировки таблицы. Прогресс отражается только текстом кнопки — полный
`render()`/снимок диагностики на каждой итерации не вызывается, чтобы не
создавать поток записей в storage.

### Audit / Diagnostics
Фиксирует действия, причины пропусков, ошибки и технические события. Ограниченный журнал разработчика связывает этапы через `operationId`; ошибка почтового API включает `mailOperation` (например, `messages.listAttachments`). Диагностический снимок добавляет окружение, счётчики и состояние UI, обезличивая пути, адреса, аккаунты, вложения и правила.

### Export
Формирует отчёты, включая экспорт в XLSX. `modules/messageReport.mjs` строит
строки листа «Письма» (единственный лист ручного и автоматического отчёта,
английские snake_case заголовки, поля `accepted_for_work`/`closure_details`
для ручного заполнения). Строки сортируются по дате получения письма от
новых к старым. `message_id` берётся из заголовка письма `Message-ID`
(RFC 5322), а не из внутреннего id Thunderbird — внутренний id не переживает
перезапуск и не следует за письмом при переносе в другую папку (см.
«Подтверждено кодом» ниже), поэтому не годится как устойчивый идентификатор.
Для старых записей, где этот заголовок ещё не был сохранён, внутренний ID
используется только для повторного чтения письма через Thunderbird; найденный
`Message-ID` записывается в отчёт, а внутренний ID не выводится никогда.
Строки с одинаковым `message_id` не схлопываются — для истории нужна полная
хронология каждого события обработки, — вместо этого повтор помечается
колонкой `duplicate_message_id` (`yes`/`no`); письма без `Message-ID` друг с
другом не сравниваются.

### Auto Report
`core/autoReportService.mjs` планирует и формирует автоматический XLSX-отчёт
по расписанию через `messenger.alarms` (`AUTO_REPORT_ALARM`, интервалы из
`AUTO_REPORT_INTERVALS`). Пересчитывает расписание при изменении `settings`
(подписка в `background.js` на `storage.onChanged`).

## Архитектурные правила восстановления

- Live не должен напрямую дублировать бизнес-логику ручной обработки.
- Ручной и автоматический режимы должны использовать единый контракт результата.
- Статистика обновляется только на основании формализованного результата обработки.
- Storage не должен самостоятельно определять пользовательскую бизнес-логику.
- Duplicate Engine должен иметь стабильный и воспроизводимый ключ.
- Audit не должен менять результат основной операции.
- Ошибка диагностического модуля не должна останавливать обработку письма.

## Подтверждено кодом (закрыто из «требует подтверждения»)

- Жизненный цикл LiveMail: нет отдельного live-менеджера — `background.js`
  напрямую подписан на `messenger.messages.onNewMailReceived`, вызывает
  единый `messageProcessingService`; актуальность правил после правки
  обеспечивает `storage.onChanged → invalidateRuntimeContext()`
  (TTL рантайм-контекста 60с, `core/messageProcessingService.mjs`).
  Старый отдельный `modules/liveMailManager.mjs` (поллинг + alarm + свой
  seen-кеш) удалён в `d533168` при переходе на единый pipeline.
- Формат duplicate key: SHA-256 фактического байтового содержимого вложения
  (`modules/duplicateManager.mjs`); fingerprint — только для совместимости
  старых записей реестра. Ключ не зависит от ящика/аккаунта: одно и то же
  вложение, пришедшее в несколько ящиков, физически сохраняется один раз —
  выигрывает то письмо, чья обработка первой дошла до `reserveExport`, и
  именно его путь сохранения (по его правилу) становится финальным,
  независимо от приоритета правил или ящиков.
- Стабильность идентификатора письма: официальная документация Thunderbird
  WebExtension API прямо называет `messages.MessageHeader.id` временным —
  «does not remain after a restart. Nor does it follow an email that has
  been moved to a different folder». Поэтому как устойчивый идентификатор
  (в отчётах, при сверке дублей строк) используется `headerMessageId`
  (заголовок `Message-ID` самого письма, RFC 5322), а не этот внутренний id.

## Требует подтверждения кодом

- фактические точки входа за пределами разобранных подсистем;
- структура persistence (нет версии схемы — см. Технический долг, S-003);
- контракт `processed/saved/skipped/error` — соответствие формализованным
  состояниям вложения (Архитектурное правило №5) на всех путях обработки;
- механизм обновления статистики за пределами `statisticsAggregator`.
